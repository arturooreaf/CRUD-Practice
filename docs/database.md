# Database

PostgreSQL accessed through Prisma. The schema is the source of truth; tables are
created and evolved via versioned migrations.

## Data model

Table `pacientes`:

| Column | Type | Notes |
|--------|------|-------|
| `id` | text (uuid) | Primary key, generated by default |
| `nombre` | text | |
| `apellidos` | text | |
| `email` | text | Unique |
| `telefono` | text | |
| `fechaNacimiento` | text | `YYYY-MM-DD` (see note below) |
| `genero` | enum `Genero` | `masculino` \| `femenino` \| `otro` |
| `grupoSanguineo` | text | Nullable |
| `alergias` | text[] | Defaults to empty array |
| `createdAt` | timestamp | Set on insert |
| `updatedAt` | timestamp | Updated on write |

The Prisma model maps to a snake-friendly table name via `@@map("pacientes")`.
`email` is declared `@unique`, which backs the API's `409` conflict behavior.

> **Note on `fechaNacimiento`:** stored as text (`YYYY-MM-DD`) to match the
> client's date input and avoid timezone conversion. A production system would
> use a native `date` column (`@db.Date`).

## Prisma workflow

```
schema.prisma  ──migrate──▶  SQL migration  ──apply──▶  PostgreSQL
       │
       └──generate──▶  typed Prisma Client (used by the API)
```

- **`prisma generate`** produces the typed client from the schema. Run as part
  of `npm run build`.
- **`prisma migrate dev`** (development) diffs the schema, generates a migration
  under `prisma/migrations/`, applies it, and regenerates the client.
- **`prisma migrate deploy`** (CI/production and the startup script) applies
  committed migrations without prompting. Idempotent.

Migrations are committed to version control so the exact schema can be recreated
anywhere with one command.

## Seeding

`prisma/seed.ts` inserts two sample patients using `upsert` keyed by `email`, so
it is safe to run repeatedly without creating duplicates. Run with
`npm run db:seed`.

## Local PostgreSQL (Docker)

`docker-compose.yml` provisions PostgreSQL 16 with credentials matching
`backend/.env.example`:

```bash
docker compose up -d      # start
docker ps                 # verify: health_crud_db is "Up (healthy)"
docker compose down       # stop (data persists in the named volume)
```

Data is stored in a named volume (`pgdata`), so it survives container restarts
and `docker compose down`.

## Connection configuration

The API reads `DATABASE_URL` from `backend/.env`:

```
postgresql://USER:PASSWORD@HOST:PORT/DATABASE?schema=public
```

`.env` is git-ignored (it holds credentials). `.env.example` is the committed
template. For a managed database (Neon, Supabase, RDS), point `DATABASE_URL` at
that instance instead — no other change required.
